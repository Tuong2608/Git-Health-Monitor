# Bản đồ Mã nguồn Từng Hàm, Tech Stack Chi tiết và Tổng quan Chức năng — Git Health Monitor

Tài liệu này giúp sinh viên tra cứu nhanh **100% các lớp và hàm trong dự án**, **lý do chọn từng công nghệ trong Tech Stack**, và **cách cài đặt VS Code Extension để vẽ sơ đồ luồng code trực quan** phục vụ kỳ vấn đáp theo Rubric Khoa CNTT.

## 2. Phân tích toàn diện Tech Stack: Dùng gì, Dùng như thế nào và Tại sao chọn?

| Tầng công nghệ | Công nghệ & Phiên bản | Sử dụng như thế nào trong dự án? | Tại sao chọn (So với phương án thay thế)? |
|---|---|---|---|
| **Ngôn ngữ & Khung Backend** | **Java 21 LTS** & **Spring Boot 4.1.1** | - Dùng `record` bất biến cho toàn bộ DTO/Model (`SnapshotData`, `FileData`, `Fact`, `Claim`).<br>- Dùng `Spring WebMVC` cho REST API, `Spring Transaction` (`@Transactional`) cho lưu trữ nguyên tử và `Spring Scheduling` (`@Scheduled`) cho `AnalysisWorker`. | - **Tại sao chọn Java 21:** Có thư viện **Eclipse JGit** thuần Java mạnh nhất để thao tác trực tiếp kho Git mà không cần gọi tiến trình `git` qua shell cho từng commit; kiểu `record` và `BigDecimal` giúp kiểm soát tính bất biến và độ chính xác số học.<br>- **Tại sao Modular Monolith:** Dự án 2 thành viên / 12 tuần chỉ cần 1 đơn vị triển khai; tránh độ trễ mạng và chi phí vận hành của Microservices. |
| **Thu thập & Phân tích lịch sử Git** | **Eclipse JGit `7.8.0.202609011348-r`** | - `GitRepositoryClient`: Clone bare repository (`setBare(true)`) về đĩa cache, fetch cập nhật mới và khóa đúng `headSha` (40 hex).<br>- `GitIngestion`: Dùng `RevWalk` duyệt đồ thị DAG theo thứ tự topo, dùng `TreeWalk` quét tập tin `.java` tại `headSha`, và dùng `DiffFormatter` + `RenameDetector` (ngưỡng tương đồng $\ge 60\%$) để nối phả hệ `lineageKey`. | - **Tại sao chọn JGit Full Bare Clone (`ADR-001`) thay vì GitHub REST/GraphQL API hay Partial Clone:** GitHub API bị giới hạn rate-limit (5.000 req/giờ) không thể quét 10.000 commit + diff từng file; Partial Clone (`blob:none`) làm `RenameDetector` và `Lizard` phải tải từng blob qua mạng rất chậm. Bare clone cục bộ chạy 10.000 commit chỉ mất `45,16 giây`. |
| **Đo độ phức tạp mã nguồn** | **Lizard `1.24.3`** (gọi qua `ProcessBuilder` với đầu ra XML) | - `LizardComplexityAnalyzer`: Trích xuất các blob `.java` tại đúng commit `headSha` ra thư mục tạm, gọi `lizard -l java --xml` với đối số tách biệt (không qua shell), parse XML bằng `DocumentBuilderFactory` (tắt XXE) để lấy `maxCcn`, `avgCcn`, `functions`, `nloc`. | - **Tại sao chọn Lizard thay vì viết bộ parser AST riêng (JavaParser/ANTLR):** Lizard là công cụ chuẩn công nghiệp, tính Cyclomatic Complexity nhanh (`2,44 giây` cho 50 file), chịu lỗi cú pháp tốt khi đọc các commit lịch sử cũ và xuất XML có cấu trúc rõ ràng. Được bọc sau abstraction nên dễ mở rộng đa ngôn ngữ về sau. |
| **Cơ sở dữ liệu & Hàng đợi Job** | **PostgreSQL 18**, **Flyway** (`V1..V4`), **Spring `JdbcTemplate`** | - Lưu 11 bảng dữ liệu quan hệ + cột `JSONB` cho bằng chứng (`evidence`, `summary`, `pinned_rules`).<br>- Dùng `JdbcTemplate` viết truy vấn SQL tường minh: `SELECT ... FOR UPDATE SKIP LOCKED` (nhận job), `ON CONFLICT DO UPDATE` (upsert `logical_file`, `contributor`), `FULL OUTER JOIN` (so sánh 2 snapshot) và `LATERAL jsonb_array_elements` (phân trang bằng chứng). | - **Tại sao chọn PostgreSQL làm luôn hàng đợi Job mà bỏ Redis (`ADR-002`):** Đảm bảo tính nguyên tử ACID giữa việc lưu 6 bảng snapshot và chuyển trạng thái job sang `SUCCEEDED` trong cùng 1 transaction; không lo lệch trạng thái giữa Redis và DB khi server restart. Chi phí lưu/so sánh ở 10k commit chỉ tốn `59,90 ms`.<br>- **Tại sao dùng `JdbcTemplate` cho tầng `monitoring`:** Cho phép kiểm soát chính xác khóa hàng `SKIP LOCKED`, cột sinh `GENERATED ALWAYS` và `FULL OUTER JOIN` mà ORM (Hibernate) khó tối ưu. |

| **Giao diện Người dùng (Frontend)** | **React 19**, **TypeScript**, **Vite 8**, **Recharts** | - `App.tsx`: Quản lý danh sách repository và form đăng ký.<br>- `AnalysisDashboard.tsx`: Hiển thị 3 tab (*Snapshot & điểm nóng*, *Giám sát & cảnh báo*, *Lịch sử phân tích*), bản đồ nhiệt, bảng chỉ số, biểu đồ xu hướng `LineChart` của Recharts và hộp thoại AI Review 3 bước.<br>- `api.ts`: Gọi `fetch` có hỗ trợ `AbortSignal` và timeout. | - **Tại sao chọn React 19 + TypeScript + Recharts:** TypeScript bắt lỗi kiểu dữ liệu ngay lúc build; Recharts hỗ trợ tốt `connectNulls={false}` và nhiều chuỗi `Line` trên cùng một trục để vẽ biểu đồ xu hướng tự động ngắt nét khi hai snapshot lệch cấu hình hoặc thiếu độ phủ. |
| **Kiểm thử, Thực nghiệm & CI/CD** | **JUnit 5**, **JaCoCo `0.8.12`**, **Playwright**, **Python `3.12`**, **Docker Compose**, **Caddy `2.9`**, **GitHub Actions**, **Gitleaks** | - `122` JUnit test + JaCoCo đo độ phủ bytecode (`89,07%`).<br>- `12` Playwright E2E test kiểm tra giao diện trên Chromium thật (cả Desktop `1440px` và Mobile `375px`).<br>- `37` Python unit test cho bộ script thực nghiệm `RQ1`, `RQ2`, `Benchmark`, `RQ3 SUS`.<br>- GitHub Actions chạy 5 job (`experiments`, `backend`, `frontend`, `secret-scan`, `package`). | - Đáp ứng trọn vẹn các tiêu chí Mức 5 của Rubric về Kiểm thử đa tầng (`TC2.5` — độ phủ lõi $\ge 70\%$), Chất lượng mã & Quét secret (`TC2.4` — Gitleaks 0 secret lộ) và Tự động hóa CI/CD (`TC2.6`). |

### 3.3. Package `com.example.demo.gitanalyzer` (Thu thập Git, Lizard & Tính Metric — Tưởng, Toản thêm CLI lịch sử)

| File / Lớp | Các hàm chính | Hàm này làm gì & Tại sao viết như vậy? |
|---|---|---|
| `GitRepositoryClient.java` | `clonePublic(...)`, `fetchPublic(...)`, `resolveDefaultBranchHead(...)` | Kiểm tra URL qua `GitHubRepositoryUrl.parse()`, dùng JGit clone bare repo với timeout cứng (`InterruptTimer`), không chạy Git hooks và trả về mã SHA 40 ký tự hex của nhánh mặc định. |
| `GitIngestion.java` | `extract(Path repoDir, String headSha, Options options)` | Duyệt `RevWalk` từ `headSha` (tối đa `maxCommits = 10.000`), sắp topo từ gốc đến ngọn để theo dõi đổi tên file qua `RenameDetector` ($\ge 60\%$), gán `lineageKey` bền vững, đánh dấu `LINEAGE_AMBIGUOUS` nếu qua merge commit có định danh cha khác nhau, và trích xuất danh sách `Fact` của các non-merge commit nằm trong `[windowStart, windowEnd)`. |
| `LizardComplexityAnalyzer.java` | `analyzeAtHead(Path repoDir, String headSha, Set<String> paths, ...)` | Trích xuất blob của các tập tin `.java` tại đúng commit `headSha` ra thư mục tạm, gọi tiến trình `lizard --xml` qua `ProcessBuilder`, parse XML an toàn để lấy `maxCcn`, `avgCcn`, `functions`, `nloc` (gán `NO_FUNCTIONS` nếu `functions == 0`). |
| `RepositoryMetricCalculator.java` | `calculate(...)`, `computeHotspotScores(...)`, `midrankPercentiles(...)`, `computeHhi(...)`, `computeTemporalCoupling(...)` | Gộp các `Fact` theo `(lineageKey, commitSha)`, tính `frequency`, `churn`, `HHI = sum(share_i^2)`, lọc cặp `Temporal Coupling` ($\text{shared} \ge 5$ và $\text{degree} \ge 0,50$), tính phân vị hạng giữa $P_{\text{change}}, P_{\text{complexity}}$ trên tập `hotspotPopulation` và tính $\text{Hotspot} = \sqrt{P_{\text{change}} \times P_{\text{complexity}}}$. |
| `GitAnalysisPipeline.java` | `analyze(Claim claim)`, `effectiveConfig()` | Kết nối `GitRepositoryClient -> GitIngestion -> LizardComplexityAnalyzer -> RepositoryMetricCalculator` thành bean `AnalysisPipeline`; ghim `pipelineVersion`, `lizardVersion`, `jgitVersion` vào chuỗi `effectiveConfigJson` để phát hiện thay đổi phiên bản công cụ. |
| `HistoricalSnapshotExport.java` *(Toản viết)* | `main(...)`, `export(...)`, `validateHistoricalHead(...)` | Công cụ CLI phục vụ thực nghiệm lịch sử RQ1 & RQ2: kiểm tra mọi tổ tiên reachable từ `headSha` đều có `committerTime < windowEnd` (chống rò rỉ dữ liệu tương lai do lệch đồng hồ Git), chạy JGit + Lizard + Metric tại đúng cây lịch sử và xuất JSON không chứa email cá nhân. |
